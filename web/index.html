Stream processing · Stream Lab

Compute over data that never ends.

Batch and stream are the same computation over bounded vs unbounded data — the difference is time and state. This lab draws the hard parts interviewers probe: event-time vs processing-time, watermarks, exactly-once (a property of the effect on state, not delivery), the probabilistic-counting toolbox, and the Lambda-vs-Kappa drift tax.

Pick a lesson in the sidebar. The driving question behind every choice: what latency does the business actually need, and what does each tier cost? Most "real-time" is really "within a few minutes" — default to batch, and escalate to streaming only when a named requirement forces it.

Windows — slicing an endless stream

You can't aggregate an infinite stream without cutting it into finite chunks. Tumbling (fixed, non-overlapping), sliding (fixed, overlapping by a slide), session (dynamic, closed by an inactivity gap). Each event lands in one tumbling window — but many sliding windows, which is the fan-out trap.

—

The proof: tumbling puts each event in exactly one bucket — cheapest state, easiest to reconcile against batch. Sliding (size 4, slide 1) puts each event in up to 4 windows — a 1-hour window with a 1-second slide is 3600× the state, so reformulate heavy sliding aggregates as one running total. Session windows close after a gap of inactivity and need a max-duration TTL or they OOM.

Event time & watermarks

A click at 12:00:59 on a phone in a tunnel arrives at 12:01:03. Bucket by processing time and it lands in the wrong minute; bucket by event time and it's correct — but now you need to know when a window is "done." A watermark (maxEventTime − lateness) asserts "I've seen everything up to here"; events behind it are late.

allowed lateness2s
—

The proof: events arrive out of order (by event time); the watermark advances as maxEventTime − lateness. When it passes a window's end, the window closes and fires. An event whose event time is behind the watermark is late — dropped or sent to a side output. Smaller lateness = lower latency but more dropped stragglers; it's a knob, not a correctness guarantee.

Joins — windowed, and the as-of trap

Stream-stream joins match two event streams within a time window (impression → click attribution) — state grows with window × throughput. Stream-table enrichment must be a temporal/as-of join: look up the dimension value as of the event's time, not the current value, or replays produce different numbers.

attribution window30s
—

The proof: a click within the window of its impression is attributed; a click that arrives after the window closes misses the join (no credit). Widen the window and you catch more — but state = window × throughput, so a wide window on a high-volume stream is a memory bomb.

Count-Min Sketch — frequency in fixed memory

"How many times did X appear?" over a huge stream, in fixed memory. Hash each item into d rows × w counters, incrementing one cell per row. The estimate is the minimum across rows (collisions only ever add, so the min is the tightest over-estimate). Slight over-count, never under.

The proof: a fixed 36-cell sketch (d=3 rows) estimates the hot items' frequencies without storing per-item counters. Because two items can hash to the same cell, a count can only be inflated — so taking the min across rows gives the tightest estimate, always ≥ the truth. Wider rows = fewer collisions = tighter estimates.

HyperLogLog — distinct count in a few KB

"How many distinct users?" over billions of events without storing them. HLL hashes each item and tracks the longest run of leading zeros seen per register — a rare long run implies a large cardinality. A few KB of registers estimates millions of distinct items to ~2%, and HLLs merge across shards.

Bloom filter — "have I seen X?"

A bit array + k hash functions. Adding X sets k bits; querying X checks those k bits. If any is 0, X is definitely not present (no false negatives). If all are 1, X is probably present (a tunable false-positive rate). Fixed memory, no stored items.

The proof: zero false negatives — if a bit is 0, the item was never added, guaranteed. The measured false-positive rate tracks the textbook (1−e^(−kn/m))^k. More bits per item drives it down exponentially. That's why a Bloom filter guards an expensive lookup (a disk/cache miss): "definitely not here" skips the query entirely.

Exactly-once — a property of state, not delivery

Exactly-once is effectively-once: each event affects state once despite replays. A checkpoint snapshots state + source offset together; on crash you rewind and replay. Whether the total is right depends entirely on the sink — a non-idempotent counter double-counts; an idempotent upsert converges.

—

The proof: the job checkpoints state + offset, processes past the checkpoint, then crashes and rewinds to the last checkpoint — replaying the in-between events. A += 1 counter counts them twice (over-count); an upsert keyed by each event's id overwrites, so the replay is a no-op and the total converges. You cannot get exactly-once from a non-idempotent, non-transactional sink — default to at-least-once + idempotent upserts, reserve 2PC for money.

Stream ⇄ table — the same data, two views

A stream is a sequence of changes (a changelog); a table is a snapshot of current state. A table is a materialized stream (fold the changelog, latest per key); a stream is a table's changelog (CDC). Log compaction makes a topic be a table.

—

KStream — changelog (every record)

KTable — latest value per key (fold)

The proof: every change appends to the stream; folding the changelog by key yields the table (latest value per key) — GROUP BY/upsert. Compaction keeps only the latest record per key, garbage-collecting the rest — the compacted log is the table. This duality is why CDC works: a database's WAL is a stream, so Debezium turns an OLTP table into an ordered event stream — retiring dual writes.

Backpressure — a feature, not a bug

When a downstream operator slows (the OLAP sink is busy), it withholds credits from upstream, cascading back to the source, which reads Kafka slower. Unconsumed records accumulate as durable Kafka lag — the pipeline degrades to higher latency, never data loss. A naive consumer with no flow control OOMs instead.

—
Kafka lag (bounded memory) per tick · sink slow ticks 4–12, then recovers

The proof: credit-based flow control cascades the throttle sink → window → map → source, so the source reads Kafka slower and the backlog sits safely in the durable log as lag — operator memory stays bounded and drains once the sink recovers. A naive consumer keeps pulling and its in-memory buffer grows without bound → OOM. Diagnose by where it originates: a slow sink → scale/ batch the sink; a slow map → it's CPU-bound. Backpressure is the symptom, not the cause.

Rollup cube — build each grain once

A dashboard needs counts by minute, hour, and day. Don't rescan the raw firehose for each — build the fine grain once, then roll up, never recount: the hour is the sum of its minutes, which is the sum of its raw events. Exactly.

—

The proof: the hourly count equals the sum of its 60 minute-buckets equals a raw recount — exactly, because count is a distributive aggregate. So you materialize the minute grain once from the firehose and derive every coarser grain by summing, never rescanning. (Averages roll up too — but keep sum + count, never average-of-averages; and distinct counts need HLL, which merges, not a plain sum.)

Lambda vs Kappa — the drift tax

Lambda runs two paths — a batch layer (exact) and a speed layer (fast, approximate) — and merges them. The flaw: the same logic lives in two codebases that drift. Kappa keeps one stream codebase over a replayable log; recompute by replaying. The staff answer is unified-code Kappa: one function, run as batch or stream.

The proof: under Lambda, the batch layer counts the late event and the speed layer (which drops it) does not — the two numbers disagree, and the serving layer must reconcile two codebases that drift every time you change the logic in one. Under Kappa there's one codebase: replaying the log yields the exact same number as a fresh run, and the same function runs as a bounded batch for backfills and an unbounded stream for live — no drift.

Schema evolution — ship independently

A field rename by one team shouldn't break fifty consumers. A schema registry stores versioned schemas and enforces compatibility at produce time. Backward compatibility (add optional fields) lets new consumers read old data and old consumers read new — no coordinated deploy. A rename is a breaking change it rejects.

—
—

The proof: adding an optional field with a default is backward-compatible — the registry accepts it, a v1 consumer ignores the new field, and a v2 consumer reads v1 data via the default. No lockstep deploy. A rename is a breaking change the registry rejects at registration, before a single bad record is produced — you handle it as a migration (add pageUrl optional, backfill, deprecate pageId). Messages carry a small schema ID, not the whole schema.
